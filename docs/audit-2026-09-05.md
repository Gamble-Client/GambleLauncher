# Launcher, loader and download-flow audit — released verification

Published 2026-09-05: launcher `0.1.133`, loader `1.4.24`, client
`1.248` / build `20260905052753`. Launcher artifact source is
`209aff4319e331dbbf3198347f4a70842589f027`; documentation-only commits
after that source do not change the published bytes. Existing immutable releases
were retained rather than overwritten.

## Implemented

- Play is an unobstructed first-run action: **Set up & play** prepares missing
  files automatically. Active profile/account, memory, mods, packs and diagnostics
  are visible. Removed the redundant client-update popup; native installation and
  verification remain authoritative.
- Fresh access is checked before Gamble launches. Dashboard sponsor requirements
  apply only to Gamble Ad Tier, not Vanilla/Fabric. Java/Flatpak refreshes sponsor
  state when the user returns. Failed refreshes stop launch visibly; repeated
  clicks and late responses cannot launch twice or overwrite a different profile.
- Dialogs have focus containment, background inertness, accessible status/progress
  and focus restoration. The Play layout fits the minimum 820×560 window and
  honors reduced motion. The existing graphite/gold visual style was retained.
- Credentials and personalized enrollment use private staging before sensitive
  bytes. Java argument files keep Minecraft tokens out of OS command lines, with
  exact quoting/native encoding and cleanup on exit/failed spawn. This does not
  encrypt tokens, sandbox installed mods, or protect against the same OS user.
- HTTP and actual ZIP expansion are bounded. Blocked redirects, empty responses
  and false lengths cannot become successful downloads. JavaFX pack listing no
  longer expands Fabric mod metadata; optional mod-name reads are bounded.
- Microsoft callback reads are bounded and cancellation-aware, including silent
  and fragmented peers. State/PKCE and trusted-origin/provenance checks remain.
- Flatpak update guidance opens `/download`, not the generic standalone JAR URL.
  README/SECURITY wording separates launcher, loader/backend, package and
  runtime responsibilities.

## Loader work in the client repository

`MemoryBootstrap` previously treated `Mixins.getConfigs()` as a permanent registry;
Sponge consumes that queue. The regression reproduces the reported
`7A8C878589` failure. The fix retains real `Config.create` handles, decorates all
required configs before normal registration, and publishes under the active
transformer monitor. It does not skip mixins or disable validation.

Tests use actual Knot and compatibility classloaders for both Fabric 0.18.2 /
Sponge 0.16.5 and the reported Fabric 0.19.3 / Sponge 0.17.3. Invalid/unsupported
configurations fail closed. Resource URLs decode percent-encoding once; signed
artifact reads enforce exact size and close streams. Diagnostics include runtime
versions and causal classes/frames without arbitrary token-bearing messages.

Windows staging now resolves the actual OS account, not a spoofable Java
`user.name`, checks the owner independently, and accepts the exact current-user
ACE under a trusted owner. Ownership repair is allowed only after validating the
object and parent ACLs. Sensitive writes use exclusively created, empty private
files; foreign owners/writers are still rejected.

Windows Java skips are POSIX-symlink, procfs-argv and full-Unicode fixtures under
legacy CP1252; native-code-page and native-JDK argument round trips pass. The live
network test is excluded from the ordinary Rust suite and was run separately.

The six account flows use synthetic fixtures. These tests include actual hosted
Windows JVM/NTFS/JNI behavior, real Fabric/Knot compatibility, installed packages
and WebView rendering. They are **not** a real Microsoft-account login or an
authenticated interactive Minecraft desktop/playthrough. Linux native tests use
the existing `.tauri-sysroot` pkg-config catalog, without changing system
networking or services.

Actual Windows tests found additional defects that Linux tests could not expose:
elevated-token files initially owned by Administrators; canonical SID aliases in
Win32 ACL serialization; and terminated child process objects still held open by
another handle. Fixes bind private empty files to the resolved current user,
canonicalize the exact expected ACL through Win32 without widening it, and use a
zero-time process wait to distinguish termination from a live process. Regression
tests include retained handles and exit code 259.

Argument files have marked child-lifetime records. Normal exit/failed spawn
cleans immediately; startup/next launch removes identified dead-child leftovers
after a previous launcher exit. Live, reused or unobservable PIDs and incomplete
spawn records are retained conservatively, not guessed from age. Inconclusive
leftovers may need manual cleanup. A post-spawn record failure aborts the child
with a bounded wait and retains files if exit cannot be confirmed.

## Security result and remaining limitations

The standard launcher source scan `6d649269-2732-47be-b359-662fcdaeafbe` validated
five low-severity findings: conditional cross-user credential-file exposure,
pre-validation loader buffering, JavaFX pack-preview expansion, OS-visible game
tokens, and callback read denial of service. Fixes are included in this release.
Native/JRE expansion and stopped-redirect handling were also fixed as robustness
defects; supplier compromise was not inflated into a new arbitrary-code-execution
finding. No paid-access or loader-provenance bypass was established.

Coverage is partial: 52 initial source/config/test/doc files were fully reviewed;
lockfiles and prebuilt binaries/assets were not exhaustively audited. TAC was
disconnected and scan token-usage measurements were unavailable. This is not an
independent certification or a claim that no vulnerabilities remain.

Longer-term hardening remains OS credential-store storage, independently signed
installers, pinned managed-Java digests and dependency/provenance review. Real
Microsoft-account/profile-override playthroughs and macOS native loading remain
manual follow-up checks. The argument-file grammar/encoding follows the
[Java 21 launcher specification](https://docs.oracle.com/en/java/javase/21/docs/specs/man/java.html#java-command-line-argument-files);
changing `file.encoding` alone does not change the native launcher parser.
